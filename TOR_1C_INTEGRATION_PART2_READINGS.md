одним запросом-ответом, не двумя разными эндпоинтами.

## 1. Важные архитектурные следствия — прочитать перед реализацией

При включённой 1С-интеграции (`ENABLE_1C_INTEGRATION=True`) меняется
поведение сразу нескольких существующих функций. Это не баги, а
осознанные решения, зафиксированные в этом разделе явно, чтобы не
потерялись между строк остального документа.

### 1.1 Локальная история показаний не используется функционально

Раньше (Excel-схема) — раздел портала «Показания» показывал предыдущее
значение и разницу (`get_pokazaniya_with_prev()`), а бот сверял новое
показание с последним сохранённым (`get_last_pokazaniya()` +
проверка «новое ≥ предыдущего»).

**При включённой 1С-интеграции обе эти функции не применяются:**
- Бот **не проверяет** новое показание на «не меньше предыдущего» — вводится как есть, любое значение
- Портал **не показывает** колонки «Предыдущее» / «Разница» для показаний этого клиента — таблица `pokazaniya` в этом режиме используется как очередь на отправку и журнал статусов, не как историческая витрина

Таблица `pokazaniya` физически продолжает хранить строки (это и есть
механизм очереди — без сохранённой записи нечего отправлять), но она не
интерпретируется как «история» для отображения или бизнес-логики.

### 1.2 Удаление счётчика — простое удаление, без сохранения истории

Раз истории показаний по счётчику всё равно не существует функционально
(п. 1.1) — при получении от 1С сигнала «счётчик удалён» соответствующая
запись в `schetchiki` удаляется напрямую (`DELETE`), без архивирования.

### 1.3 Старая заглушка в `bot.py` — удалить

`_task_sync_readings_to_1c` в `bot.py` (пустая заглушка, зарегистрированная
в APScheduler ещё на раннем этапе проекта) — убрать полностью. Реальная
задача синхронизации регистрируется в APScheduler **внутри `api/main.py`**,
не в `bot.py` — согласно решению из Части 1 «вся интеграция с 1С живёт в
FastAPI-процессе, бот про 1С не знает вообще».

## 2. Раздел для Python-разработчика

### 2.1 Изменения схемы БД

`database.py`, таблица `pokazaniya` — добавить три колонки:

```sql
ALTER TABLE pokazaniya ADD COLUMN sent_to_1c INTEGER DEFAULT 0;
ALTER TABLE pokazaniya ADD COLUMN status_1c  TEXT DEFAULT NULL;  -- NULL | 'accepted' | 'rejected'
ALTER TABLE pokazaniya ADD COLUMN batch_id   TEXT DEFAULT NULL;
```

При `ENABLE_1C_INTEGRATION=False` эти колонки просто не используются —
поведение полностью как сейчас, изменений в текущем флоу нет.

### 2.2 Формирование пакета — алгоритм задачи

Задача **одна**, зарегистрирована в APScheduler внутри `api/main.py`,
запускается **каждый час** (не «раз в сутки с отдельным почасовым
ретраем» — это один и тот же job с внутренней логикой, что упрощает
код и физически исключает двойной запуск):

```python
def sync_1c_job():
    state = get_1c_sync_state()  # last_success_at, last_attempt_at, pending_batch_id

    is_retry = state["pending_batch_id"] is not None
    due_for_daily_run = (now() - state["last_success_at"]) >= timedelta(hours=24)

    if not is_retry and not due_for_daily_run:
        return  # ничего не делаем, ещё не время

    if is_retry:
        # Повторная попытка — тот же batch_id, тот же набор показаний,
        # что и при первой неудавшейся попытке. Новые показания,
        # поступившие за время простоя, в этот пакет НЕ добавляются —
        # они уйдут со следующим успешным циклом.
        batch_id, readings = state["pending_batch_id"], get_readings_by_batch(state["pending_batch_id"])
    else:
        # Обычный суточный запуск — свежая выборка
        cutoff = now()
        readings = get_unsent_readings(created_before=cutoff)
        batch_id = generate_batch_id()  # например "20260809-01"

    result, err = client_1c.sync_readings(batch_id, readings)

    if err:
        # 1С недоступна — фиксируем pending_batch_id, следующий запуск
        # через час автоматически станет ретраем этого же пакета
        save_1c_sync_state(pending_batch_id=batch_id, last_attempt_at=now())
        if state["pending_batch_id"] is None:
            # Это первая неудача — не была ретраем до этого момента
            log.error("1С недоступна при первой попытке синхронизации, batch_id=%s", batch_id)
            # TODO: канал оповещения администратора — см. открытый вопрос 4.3
        return

    apply_readings_statuses(result["readings_status"])   # UPDATE pokazaniya + уведомление в MAX
    apply_meters_changes(result["meters_changes"])        # INSERT/UPDATE/DELETE в schetchiki
    save_1c_sync_state(pending_batch_id=None, last_success_at=now())
```

**Важно:** переход из режима «раз в сутки» в режим «ретрай каждый час»
происходит автоматически по факту первой неудачи — не требует отдельного
переключателя. После первого успешного ответа `pending_batch_id`
сбрасывается, и следующий запуск снова будет обычным суточным (через 24
часа от момента успеха).

### 2.3 Новый эндпоинт FastAPI (для внутреннего использования задачей)

Или прямой вызов `client_1c.py` из задачи APScheduler — эндпоинт FastAPI
здесь не обязателен, поскольку задача уже выполняется в том же процессе.
Достаточно функции:

```python
def sync_readings(batch_id: str, readings: list[dict]) -> tuple[dict | None, str | None]:
    """POST {INTEGRATION_1C_BASE_URL}/readings/sync"""
```

### 2.4 Применение статусов (`apply_readings_statuses`)

Для каждой записи в `result["readings_status"]`:
1. Найти строку в `pokazaniya` по естественному ключу (`ls` + `meter_number` + `value1`/`value2` + `submitted_at`, где `submitted_at` — момент передачи показания клиентом, сохранённый при создании строки)
2. Проставить `status_1c` (`'accepted'` / `'rejected'`) и `sent_to_1c=1`
3. Отправить клиенту в MAX уведомление:
   - принято: `"✅ Ваши показания по счётчику {resource_type} №{meter_number} приняты."`
   - отклонено: `"❌ Ваши показания по счётчику {resource_type} №{meter_number} не приняты."` (без указания причины — обобщённая формулировка, причина от 1С не передаётся и не запрашивается в этой версии)

### 2.5 Применение изменений счётчиков (`apply_meters_changes`)

Для каждой записи в `result["meters_changes"]` по полю `action`:
- `"added"` → `INSERT` в `schetchiki` (если ещё нет такой пары `ls`+`meter_number`)
- `"changed"` → `UPDATE` полей `resource_type`/`meter_type` по `ls`+`meter_number`
- `"removed"` → `DELETE` из `schetchiki` по `ls`+`meter_number` (без архивирования, см. п. 1.2)

### 2.6 Состояние синхронизации

Нужна одна строка состояния (не таблица per-batch, просто текущий статус
процесса) — можно как отдельная маленькая таблица `sync_1c_state` с
единственной строкой, либо через `config`-подобный key-value. Поля:
`last_success_at`, `last_attempt_at`, `pending_batch_id`.

### 2.7 Оповещение администратора о первой неудаче

Требование — сигнализировать **после первой же неудачной попытки**, не
дожидаясь долгого простоя. В базовой реализации — заметная запись
`log.error(...)`. Если нужен более заметный канал (письмо администратору,
баннер в портале) — это отдельная задача вне рамок текущего ТЗ, здесь
фиксируется только гарантированно работающий минимум через лог.

### 2.8 UI портала — что скорректировать

В шаблоне `pokazaniya.html` при `ENABLE_1C_INTEGRATION=True` колонки
«Предыдущее» и «Разница» не показывают осмысленных данных (см. п. 1.1) —
предложение: скрывать эти две колонки полностью для инсталляций с
включённой интеграцией, показывая вместо них колонку «Статус 1С»
(Ожидает / Принято / Отклонено, по полю `status_1c`).

## 3. Раздел для 1С-разработчика

### 3.1 `POST /readings/sync`

Один комбинированный эндпоинт — принимает пакет показаний, возвращает и
статусы по ним, и дельту изменений состава счётчиков, в одном ответе.

**Требование по идемпотентности — обязательное.** Если вы получаете
запрос с `batch_id`, который уже был вами обработан ранее (наш повторный
запрос после того как ответ не дошёл до нас по сети) — **не создавайте
показания повторно**. Определите по `batch_id`, что пакет уже
обрабатывался, и просто верните тот же результат ещё раз.

```json
// Запрос от нас к вам
{
  "batch_id": "20260809-01",
  "readings": [
    {
      "chat_id": 123456789,
      "ls": "100001",
      "meter_number": "СЭ-001",
      "value1": "150.0",
      "value2": null,
      "submitted_at": "2026-08-09 14:32"
    },
    {
      "chat_id": 987654321,
      "ls": "100002",
      "meter_number": "ХВ-004",
      "value1": "80.0",
      "value2": null,
      "submitted_at": "2026-08-09 09:10"
    }
  ]
}
```

```json
// Ваш ответ
{
  "batch_id": "20260809-01",
  "readings_status": [
    {
      "ls": "100001",
      "meter_number": "СЭ-001",
      "value1": "150.0",
      "submitted_at": "2026-08-09 14:32",
      "status": "accepted"
    },
    {
      "ls": "100002",
      "meter_number": "ХВ-004",
      "value1": "80.0",
      "submitted_at": "2026-08-09 09:10",
      "status": "rejected"
    }
  ],
  "meters_changes": [
    {
      "ls": "100001",
      "action": "added",
      "meter_number": "СЭ-003",
      "resource_type": "Электроэнергия",
      "meter_type": "Однотарифный"
    },
    {
      "ls": "100002",
      "action": "removed",
      "meter_number": "ХВ-002"
    },
    {
      "ls": "100003",
      "action": "changed",
      "meter_number": "СЭ-005",
      "resource_type": "Электроэнергия",
      "meter_type": "Двухтарифный"
    }
  ]
}
```

**Поле `status`** в `readings_status` — строго `"accepted"` или
`"rejected"`. Причина отклонения текстом **не передаётся** — на нашей
стороне клиенту в любом случае показывается обобщённая формулировка «не
принято», без деталей.

**`meters_changes`** — только дельта за период с прошлого успешного
обмена, не полный список счётчиков. Поле `action` — одно из `"added"` /
`"changed"` / `"removed"`. Для `"removed"` достаточно `ls` +
`meter_number`, остальные поля не нужны.

### 3.2 Требование по времени ответа

В отличие от авторизации (Часть 1, таймаут 5 сек — это интерактивный
диалог с пользователем), здесь запрос идёт из фонового процесса без
участия человека в реальном времени. Жёсткого требования в 5 секунд нет,
но сообщите ожидаемое время обработки пакета — это нужно нам для
настройки таймаута на своей стороне (пакет может быть большим, если
клиентов много).

### 3.3 Обработка вашей стороной

1. Провести документы по каждому показанию из `readings[]`, определить принято/отклонено
2. Сформировать дельту по составу счётчиков с момента последнего успешного обмена с нами (нужно хранить у себя отметку «когда мы в последний раз успешно ответили этому серверу», раз это дельта, а не полный снимок)
3. Вернуть результат в указанном формате

## 4. Открытые вопросы к моменту начала разработки

1. Ожидаемое время обработки пакета на стороне 1С (для настройки таймаута)
2. Максимальный ожидаемый размер пакета (сколько показаний может накопиться за сутки у одного клиента) — не блокирует разработку, но полезно для оценки
3. Подтверждение от 1С-стороны, что дельта по счётчикам технически реализуема (хранение отметки последней успешной синхронизации по каждому подключённому серверу)
4. Канал оповещения администратора о простое 1С сверх обычного лога — если появится потребность в более заметном канале, обсуждается отдельно

## 5. Что НЕ входит в эту часть ТЗ

- Причины отклонения показаний текстом — не передаются, не отображаются
- Повторная отправка отклонённых показаний — отклонено считается финальным статусом
- Архивирование истории по удалённым счётчикам — истории функционально не существует (п. 1.1–1.2)
- Отображение «предыдущее значение / разница» при включённой 1С-интеграции — сознательно убрано из UI (п. 2.8)
