# GitHub-инфраструктура и процесс изменений

Этот документ описывает управление кодом, Pull Request, проверками и секретами.
Развёртывание Docker-контуров описано отдельно в [DEPLOYMENT.md](../DEPLOYMENT.md),
а роли агентов — в [AGENTS.md](../AGENTS.md).

## Фактическое состояние

На момент создания документа:

- `main` — единственный источник кода для развёртывания;
- CI определён в [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) и
  запускается для PR и push в `main`, `integration/**` и `review/**`;
- обязательная работа CI выполняется job с точным именем
  **`Tests and quality checks`**;
- production-секреты CI не требуются: тесты используют безопасные тестовые
  значения и mock 1С;
- один сервер содержит два изолированных Docker-контура: `test` и `prod`;
- защита ветки `main` и GitHub ruleset **пока не включены**. Настройки ниже
  являются целевыми рекомендациями, а не описанием уже действующих ограничений.

## Ветки и жизненный цикл

Формат имени: `<тип>/<краткое-описание-kebab-case>`. Для привязки к задаче
можно добавить номер: `fix/123-timeout-1c`.

| Префикс | Назначение |
| --- | --- |
| `feature/` | Новая функциональность |
| `fix/` | Исправление дефекта |
| `hotfix/` | Срочное production-исправление |
| `docs/` | Только документация |
| `integration/` | Временное объединение нескольких готовых веток |
| `review/` | Временные исправления по результатам ревью |

Правила:

1. Любая рабочая ветка создаётся от актуального `main`.
2. Ветка решает одну связанную задачу; несвязанные изменения разделяются.
3. Разработчик регулярно подтягивает `main` и разрешает конфликты в своей ветке.
4. Обычные `feature/**`, `fix/**`, `docs/**` и `hotfix/**` направляются
   отдельным PR непосредственно в `main`. Прямой push в `main` после включения
   защиты запрещён.
5. `integration/**` — редкое временное исключение для объединения нескольких
   готовых веток. Каждая ветка попадает в `integration/**` только через PR с
   теми же требованиями CI и независимого ревью; после общей проверки открывается
   один финальный PR из `integration/**` в `main`.
6. `review/**` содержит исправления по замечаниям конкретного PR и возвращается
   в этот же PR либо сливается в его исходную ветку через PR. Это не отдельный
   путь в `main` и не обход CI или ревью.
7. `integration/**` и `review/**` не являются источниками развёртывания.
8. После слияния и подтверждения работоспособности удалённая рабочая ветка
   удаляется. Долгоживущих веток, дублирующих `main`, не создаём.
9. `hotfix/**` проходит тот же CI и PR; срочность не отменяет проверок.

## Pull Request

1. Автор обновляет ветку от `main`, формулирует цель, риски, способ проверки и
   влияние на БД, конфигурацию и внешние интеграции.
2. Незавершённая работа открывается как Draft.
3. Перед переводом в Ready выполнены локальные проверки, тесты добавлены или
   объяснено, почему они не нужны.
4. Процесс ролей из [AGENTS.md](../AGENTS.md) обязателен: разработчик реализует,
   независимый ревьюер проверяет diff, тестировщик независимо запускает проверки,
   координатор принимает результат.
5. PR нельзя сливать при P0/P1, падающем CI или нерешённых обсуждениях. P2
   исправляется либо явно принимается владельцем проекта с описанием риска.
6. После одобрения и зелёного `Tests and quality checks` PR сливается выбранным
   единообразным методом; ветка удаляется.

### Чек-лист PR

- [ ] Изменение ограничено заявленной задачей.
- [ ] Нет токенов, паролей, персональных данных, SQLite-баз и документов клиентов.
- [ ] Обновлены тесты и документация.
- [ ] Описаны миграции и обратная совместимость.
- [ ] Пройден `Tests and quality checks`.
- [ ] Получено минимум одно независимое одобрение.
- [ ] Все обсуждения разрешены, P0/P1 отсутствуют, P2 устранены или приняты.
- [ ] Указаны известные ограничения и план отката.

## Рекомендуемая защита `main`

Создать GitHub ruleset для ветки `main`:

- требовать Pull Request;
- требовать минимум **1 approval**;
- сбрасывать approvals при появлении новых коммитов (**dismiss stale approvals**);
- требовать разрешения всех обсуждений (**conversation resolution**);
- требовать status check **`Tests and quality checks`** и актуальность ветки
  перед слиянием;
- запрещать force-push и удаление `main`;
- не разрешать обычный прямой push;
- применять правила ко всем участникам. Административный bypass использовать
  только при аварии, с зафиксированной причиной и последующим PR/разбором.

После настройки ruleset его фактические параметры следует сверить с этим
разделом и обновить отметку в разделе «Фактическое состояние».

## Сервер и продвижение релиза

Единственный разрешённый источник обоих контуров — проверенный commit из
`main`. На одном сервере контуры изолированы разными Compose-проектами,
env-файлами, портами и runtime-каталогами, как описано в
[DEPLOYMENT.md](../DEPLOYMENT.md).

Порядок продвижения:

1. Зафиксировать полный SHA проверенного commit из `main`.
2. Создать и проверить backup контура `test`.
3. Развернуть **этот SHA** в `test`, выполнить health-check и smoke-тесты.
4. После приёмки создать и проверить backup `prod`.
5. Развернуть в `prod` тот же SHA без дополнительных изменений.
6. Проверить health, логи, MAX-бота, API/web и интеграцию 1С.
7. При сбое остановить продвижение и откатить код на последний проверенный commit,
   восстановив данные из проверенного backup, если миграция затронула данные.

Не разворачивать production напрямую из рабочей ветки или непроверенного
локального состояния.

### Чек-лист релиза

- [ ] Commit принадлежит `main`, SHA записан.
- [ ] CI для commit зелёный.
- [ ] Backup создан и прошёл проверку целостности.
- [ ] Этот SHA успешно проверен в `test`.
- [ ] Health-check и критические smoke-сценарии `test` пройдены.
- [ ] Для `prod` согласовано окно и ответственный за откат.
- [ ] В `prod` развёрнут тот же SHA.
- [ ] Health-check, логи и внешние интеграции `prod` проверены.
- [ ] Результат релиза и возможный откат зафиксированы.

## Секреты

### Текущее хранение

Runtime-секреты приложения находятся **только на сервере** в файлах конкретного
контура: `.env`, `.env.test`, `.env.prod.runtime` и
`.env.test.runtime`. Они не коммитятся и не копируются в PR, логи или
артефакты CI.

| Данные | Где хранить |
| --- | --- |
| `TOKEN` MAX | Серверный env-файл соответствующего контура |
| `SECRET_KEY` | Серверный env-файл соответствующего контура |
| `INTERNAL_API_TOKEN` | Серверный env-файл соответствующего контура |
| `INTEGRATION_1C_BASE_URL` | Серверный env-файл соответствующего контура |
| `INTEGRATION_1C_AUTH_TOKEN` | Серверный env-файл соответствующего контура |
| `BOOTSTRAP_ADMIN_PASSWORD` | Только `.env.*.runtime`, временно до первого входа |

У `test` и `prod` должны быть разные значения. После первого входа
`BOOTSTRAP_ADMIN_PASSWORD` очищается и контейнеры пересоздаются. Текущий CI не
нуждается в production secrets и не должен получать их.

### Будущий автоматический deploy

Если будет добавлен deploy из GitHub Actions:

- создать GitHub Environments `test` и `prod`;
- хранить раздельные environment-specific SSH credentials и `known_hosts`;
- для `prod` включить required reviewer/ручное approval;
- ограничить deploy проверенным commit из `main`: сначала `test`, затем
  `prod`;
- выдавать workflow минимальные permissions;
- не переносить runtime-секреты приложения в GitHub Actions без технической
  необходимости: предпочтительно оставить их в защищённых серверных env-файлах.

### Доступ, ротация и инциденты

- Доступ к GitHub Environments и серверным env-файлам получают только
  ответственные за развёртывание; доступ пересматривается при изменении команды.
- Права предоставляются по принципу минимальной необходимости.
- Секреты ротируются при смене ответственного, подозрении на утечку и по
  установленному регламенту; `test` и `prod` ротируются отдельно.
- При инциденте: отозвать/заменить секрет, остановить затронутый deploy,
  проверить Git-историю, Actions-логи и серверные логи, оценить воздействие,
  восстановить работу и зафиксировать разбор.
- Если секрет попал в Git, одного удаления файла недостаточно: секрет немедленно
  отзывается и заменяется, затем очищается история по согласованной процедуре.
